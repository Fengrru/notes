**NeuroLux** 是一个 Minecraft 模组（NeoForge），它用单次前向的 3D CNN 推理取代了原版的广度优先搜索（BFS）光照传播。这个项目是一个研究原型：它并不声称能直接替换生产环境中的世界，而是演示了一个神经网络如何被嵌进真实的游戏引擎循环里，去承担传统上靠手写算法完成的物理模拟工作。

这篇文章会讲清楚：为什么这个问题很难、模型是怎么训练的，以及模组如何在不破坏引擎的前提下接入 Minecraft。

## 1. 为什么要替换 BFS？

Minecraft 的光照引擎，核心就是在 16×16×16 的子区块上做迭代式 BFS。每当一个方块发生变化：

1. 引擎扫描受影响的子区块。
2. 把光照传播到相邻的 6 个方块。
3. 反复重新扫描，直到光照值收敛。
4. 递归地触发相邻子区块。

对一支火把来说，这很便宜。但对大型红石装置、连锁反应、TNT 爆炸，或者批量加载区块来说，同一套逻辑会在大量相互依赖的子区块上反复运行。结果就是肉眼可见的 TPS 掉帧，在光照更新容易堆积的模组服务器上尤其明显。

问题在于：神经网络能不能直接从**方块状态**学出**最终**的光照场，把这个迭代过程变成一次前向传播？

## 2. 混合方案

最天真的第一版做法是完全去掉 BFS，让 CNN 预测一切。这行不通，因为 CNN 只能看到一个 16×16×16 的子区块。相邻子区块里的光源、跨子区块的传播，以及驱动区块渲染和客户端同步的内部状态，全都会丢失。

所以 NeuroLux 采用的是一条混合流水线：

1. **原版 BFS 依然先跑**。它负责跨子区块传播、区块状态管理，以及客户端-服务端同步。
2. **BFS 返回之后**，CNN 重新计算任何含有光源的子区块。
3. **CNN 的输出覆盖掉** BFS 刚写入的 DataLayer 数值。

这意味着模组永远不会破坏内部状态机。如果 CNN 算错了，最坏情况是某个子区块出现渲染瑕疵；引擎本身照常运行。而如果 CNN 连续失败，模组会自动回退到原版 BFS。

## 3. 模型架构：一个 3D U-Net

模型 `LightPropNet` 是一个 3D U-Net 编码器-解码器。输入是形状为 `[B, 5, 16, 16, 16]` 的张量，输出是 `[B, 2, 16, 16, 16]`。

### 输入通道（每个方块）

| 通道 | 特征 | 范围 |
|---------|---------|-------|
| 0 | `light_emission` | 0–1（从 0–15 归一化） |
| 1 | `light_opacity` | 0–1 |
| 2 | `is_solid` | 0 或 1 |
| 3 | `propagates_sky` | 0 或 1 |
| 4 | `is_air` | 0 或 1 |

这五个通道编码了网络在光照这件事上需要知道的关于一个方块的一切：它是否发光、遮挡多少光、是否不透光、天光能否穿过，以及它是不是空气。

### 网络结构

```
Input  [B, 5,  16, 16, 16]
  ↓ enc1 (stride 1)  [B, 32, 16, 16, 16]  ← skip
   enc2 (stride 2)  [B, 64,  8,  8,  8]  ← skip
  ↓ enc3 (stride 2)  [B, 128, 4,  4,  4]  ← skip
  ↓ enc4 (stride 2)  [B, 256, 2,  2,  2]
  ↓ bottleneck       [B, 256, 2,  2,  2]
  ↓ dec1 + skip(e3)  [B, 256, 4,  4,  4]
  ↓ dec2 + skip(e2)  [B, 128, 8,  8,  8]
  ↓ dec3 + skip(e1)  [B, 64, 16, 16, 16]
  ↓ out conv + Sigmoid
Output [B, 2,  16, 16, 16]
```

两个输出通道是 `block_light` 和 `sky_light`，都在 `[0, 1]` 区间，之后会被重新缩放到 0–15 范围。这里 U-Net 的设计很关键，因为光照有非常尖锐的空间结构：明亮的光源、漆黑的遮挡物，以及很长的衰减尾巴。跳跃连接保留了编码器里的高频空间细节，让解码器能准确地放置光照边界。

总参数量约 **4.38M**，导出的 ONNX 模型约 **16.7MB**。

## 4. 用合成数据训练

训练不需要运行一个 Minecraft 实例。项目里包含一个合成数据生成器，它随机生成 16×16×16 的场景，并跑自己的 BFS 来产出真值光照图。

### 场景类型

生成器产出三类场景：

- **开阔天空**：平坦地形，零星树木，暴露在天光下。
- **洞穴**：石头外壳，中间是不规则挖空的空气腔，墙上插着火把。
- **房间**：封闭的石屋，有玻璃窗、红石灯、荧石和地面火把。

方块调色板包含 26 种类型，从空气、石头到水、玻璃、树叶、岩浆、红石灯和羊毛。每种方块类型都有固定的发光、遮挡、固体、透天光和空气标记。

### BFS 真值

两遍独立的流程产出标签：

- **方块光**：从每个发光方块出发做 6 邻域 BFS，每步减去遮挡值。
- **天光**：从顶面向下扫，穿过透明方块时按遮挡值递减，遇到不透光方块停止。

结果是形状为 `[2, 16, 16, 16]` 的目标张量，包含原始的 0–15 光照值。

### 损失函数与训练

训练目标是 L1 加上一个梯度一致性项：

```
L = L1(pred × 15, target) + λ · gradient_loss(pred × 15, target)
```

L1 项迫使网络预测出正确的光照等级。梯度项迫使网络匹配光照场的空间**梯度**，这在阴影边界和明暗过渡处很重要。实践中 `λ = 0.1`。

训练使用 AdamW，配合余弦退火和梯度裁剪。在合成验证数据上，最终 checkpoint 达到：

- **MAE**：约 0.026 / 15.0（约 0.40 个光照等级）
- **±1 容差准确率**：99.6%
- **精确准确率**：约 3.3%

精确准确率低，是因为这本质上是在一个连续区间上做回归：偏出一个量化后的光照等级非常常见。±1 准确率说明，对实际光照来说，网络的预测几乎总是与真值相差不超过一档。

## 5. 把模型接入 Minecraft

运行时这一侧是用 Java 写的 NeoForge 模组。它用 **Mixin** 在 `LevelLightEngine` 的两个位置注入：

```java
// 1. When a block changes, enqueue its subchunk
@Inject(method = "checkBlock", at = @At("HEAD"))
private void onCheckBlock(BlockPos pos, CallbackInfo ci) {
    NeuroLuxEngine.enqueueSection(SectionPos.of(pos));
}

// 2. After BFS finishes, process the queue and overwrite the DataLayer
@Inject(method = "runLightUpdates", at = @At("RETURN"))
private void onRunLightUpdates(CallbackInfoReturnable<Integer> cir) {
    NeuroLuxEngine.processPendingInferences(level, self);
}
```

`processPendingInferences` 流水线的流程是这样的：

1. 在服务端线程上，从子区块中**抽取** 5 通道的方块状态张量。
2. 把 ONNX 推理任务**提交**给单线程的后台执行器（ONNX Runtime 的 session 不是线程安全的）。
3. 通过**回调**把 DataLayer 的写回调度回服务端线程。
4. 把预测出的 0–15 的 `block_light` 和 `sky_light` 值**写入**光照引擎的 nibble 数组。
5. 把区块**标记**为未保存，触发客户端同步和落盘。

这套线程模型很重要：真正的推理可以放在后台跑，但对世界状态的每一次写入，都必须发生在服务端线程上，以避免与区块加载和渲染器产生竞态。

### 回退与安全

一个 `consecutiveFailures` 计数器跟踪推理失败次数。一旦超过可配置的阈值（默认 10），模组就启用原版 BFS 回退。如果之后某次推理成功，模组会关闭回退。另外，世界加载后有 10 秒的宽限期，避免在启动时区块加载的洪峰期跑神经推理。

## 6. ONNX Runtime 与部署

训练好的 PyTorch 模型通过一个专门的脚本导出为 ONNX。导出过程：

- 默认使用 opset 17。
- 支持可选的 FP16 量化。
- 把权重直接嵌进 `.onnx` 文件，这样模组既能从 classpath 加载，也能从 `config/neurolux/` 目录加载。

运行时，模组用 ONNX Runtime 加载模型。它先试 CUDA；如果失败，或者配置里禁用了 GPU，就回退到 CPU。CPU 推理可以跑，但可能比原版 BFS 还慢——这也是推荐用 GPU 的原因。

推理耗时估计（高度依赖硬件）：

- GPU：每个子区块约 2–5 ms
- CPU：每个子区块约 15–30 ms

## 7. 局限，以及为什么它只是原型

README 里对项目的局限很诚实，这些值得再重复一遍：

- **单子区块盲区**：模型只能看到一个 16³ 的体积。相邻子区块的光源不可见，可能造成边界处的接缝。
- **只用合成数据训练**：模型没有在真实的 Minecraft 世界或边界情况上训练过。
- **渲染瑕疵**：神经预测可能在子区块边界处与 BFS 不一致，产生暗斑或断裂。
- **模组兼容性**：很可能与 Iris、OptiFine 冲突，尤其是同样重写了光照引擎的 Starlight。
- **不感知红石**：受红石控制的光源没有被建模。
- **CPU 回退**：没有 GPU 时，模组可能比原版还慢。

这些不是无关紧要的脚注；它们界定了研究原型和生产级模组之间的边界。NeuroLux 是有用的概念验证，而非可以直接替换的优化。

## 8. 这个项目意味着什么

对我来说，NeuroLux 是一次用学习到的模拟取代算法模拟的实验。有意思的地方不在于 CNN 能逼近 BFS——这是意料之中的。有意思的是这件事能在游戏循环**内部**完成，让原算法继续作为安全网运行，并且在学到的模型失效时有一条明确的回退路径。

这个架构是刻意保守的：神经网络是一个可选的后处理器，而不是替代品。正是这个选择，让它可以在不冒任何世界状态损坏风险的前提下被部署、调试和度量。
